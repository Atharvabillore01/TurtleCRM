1. DOCKER COMPOSE EXTENSION: Why React Apps Need to be Services
================================================================================

CURRENT STATE:
- docker-compose.yml has PostgreSQL, Redis, Zookeeper, Kafka, and 4 backend 
  services (auth, otp, user, notification)
- MISSING: client-app and advisor-app are NOT in docker-compose

WHY THEY NEED TO BE ADDED:

The FULL DEPLOYMENT FLOW is:
  Browser → React App (port 3000/3001) 
          → Vite Dev Server (or built static) 
          → Axios calls to /auth endpoints 
          → Auth-Service (port 4000)

WITHOUT Docker Services for Apps:
  ❌ When you docker-compose up, only backend services run
  ❌ You'd need to manually start pnpm dev in apps/client-app separately
  ❌ No unified orchestration — inconsistent environment (dev vs prod)
  ❌ Can't environment-switch the app URLs easily

WITH Docker Services for Apps:
  ✅ docker-compose up --build = TRUE full-stack startup — everything in one command
  ✅ Apps can reference services by hostname (auth-service:4000 inside docker network)
  ✅ Apps see consistent .env (DATABASE_URL, KAFKA_BROKERS, etc.)
  ✅ Healthcheck on apps ensures they're ready before tests run

SERVICE DEPENDENCIES:
  client-app & advisor-app 
    ↓ depend_on
  auth-service
    ↓ depends_on
  postgres, redis, kafka

This DAG ensures Kafka/Redis are healthy before auth-service starts, and 
auth-service is healthy before apps attempt to connect.

2. DOCKERFILE STRATEGY: Frontend vs Backend Patterns
================================================================================

WHY DIFFERENT?

REACT APPS (Client-App / Advisor-App):
Need VITE PREVIEW SERVER (not Node.js dev server):

  FROM node:20-alpine
  WORKDIR /app
  COPY package*.json pnpm-lock.yaml ./
  RUN pnpm install --prod
  COPY . .
  RUN pnpm build           # ← Creates optimized dist/
  EXPOSE 3000
  CMD ["pnpm", "preview"]  # ← Serves dist/ as static SPA

WHY THIS PATTERN:
  • pnpm build = Vite bundling + tree-shaking (optimized for production)
  • pnpm preview = Lightweight server serving dist/ folder
  • Not running full Vite dev server (which needs source maps & hot reload)
  • Result: ~50MB image instead of 500MB with node_modules

PRODUCTION BEHAVIOR:
  Browser GET /          → Vite Preview serves dist/index.html
  Browser GET /auth/...  → Vite proxy (configured in vite.config.ts)
                            → Proxies to auth-service:4000 (Docker DNS)

BACKEND SERVICES (Node.js + TypeScript):
Pattern: COMPILE THEN RUN

  FROM node:20-alpine
  WORKDIR /app
  COPY package*.json pnpm-lock.yaml ./
  RUN pnpm install --prod
  COPY . .
  RUN npm run build      # ← tsc compiles src/ to dist/
  EXPOSE 4000
  CMD ["node", "dist/index.js"]

WHY:
  • Services run COMPILED JAVASCRIPT (TypeScript → JS at build time)
  • No tsc at runtime (faster startup, smaller memory)
  • Healthcheck endpoints (/health) return { status: "ok" }

3. ROOT README: Why Documentation Matters for This Monorepo
================================================================================

WHAT THE README ACCOMPLISHES:

A. PREREQUISITES SECTION:
Prevents: "It doesn't work on my machine"
  • Docker 25+ (Compose v2)
  • Node 20+ (LTS)
  • pnpm 8+ (workspace resolver)

WHY THESE MATTER:
  • Docker 25+ has improved Compose syntax for healthchecks
  • Node 20 is what .node-version and CI target
  • pnpm workspaces resolve @turtle/* aliases (npm/yarn would fail)

B. QUICK START: THE SINGLE HAPPY PATH:
  git clone https://github.com/.../turtle-corporate
  cp .env.example .env       # ← Uses sensible dev defaults
  docker-compose up --build  # ← One command = everything

OPENS 6 PORTS:
  • 3000  — client-app (OTP auth)
  • 3001  — advisor-app (username + password + OTP + OAuth)
  • 4000  — auth-service (JWT issuer)
  • 5432  — PostgreSQL (development database)
  • 6379  — Redis (sessions + OTP cache)
  • 9092  — Kafka (event bus)

C. SERVICE PORTS TABLE:
Why explicit?
  • Auth-Service (4000): Issues JWTs, validates OTP, handles OAuth redirect
  • OTP-Service (4001): Consumes Kafka OTPRequested events, calls Twilio/AWS/MSG91
  • User-Service (4002): CRUD users, profile, stores in PostgreSQL
  • Notification-Service (4003): Consumes LoginSuccess events, sends emails via SendGrid
  • PostgreSQL (5432): Persistent user data
  • Redis (6379): JWT refresh tokens (FASTER than DB), OTP cache (TTL), 
                   rate-limit buckets
  • Kafka (9092): Event sourcing — decouples services

D. HOW TO SWITCH OTP_PROVIDER:
  OTP_PROVIDER=mock      # Dev: prints OTP to logs
  OTP_PROVIDER=twilio    # Prod: SMS via Twilio
  OTP_PROVIDER=msg91     # India: MSG91 SMS
  OTP_PROVIDER=aws       # AWS SNS

WHY THIS MATTERS:
  • Different providers have different credentials
  • Each .env line (TWILIO_ACCOUNT_SID, MSG91_AUTH_KEY) is provider-specific
  • Docs explain which credentials you need for each

E. HOW TO SWITCH EVENT_BUS:
  EVENT_BUS=kafka      # Default: Kafka (scalable, persistent topics)
  EVENT_BUS=rabbitmq   # Alternative: RabbitMQ (queues, more traditional)

WHY BOTH?
  • Kafka = append-only log, event replay, partitions
  • RabbitMQ = traditional queues, ACKs, simpler setup
  • README explains trade-offs

F. LOCAL DEVELOPMENT (pnpm dev):
  # WITHOUT Docker:
  pnpm dev               # Starts all services w/ tsx watch

  # Each service watches src/ → rebundles on change
  apps/client-app:       Vite HMR on :3000
  apps/advisor-app:      Vite HMR on :3001
  services/auth-service: tsx watch on :4000

WHY INCLUDE THIS?
  • Faster iteration (HMR, faster rebuild)
  • No Docker overhead
  • Easier debugging (logs in terminal)
  • BUT requires PostgreSQL/Redis/Kafka running locally (complexity trade-off)

4. CROSS-PACKAGE IMPORTS: Path Aliases & Resolution
================================================================================

CURRENT SETUP IN TSCONFIG.BASE.JSON:
  {
    "compilerOptions": {
      "paths": {
        "@turtle/types":  ["./packages/types/src/index.ts"],
        "@turtle/config": ["./packages/config/src/index.ts"],
        "@turtle/ui":     ["./packages/ui/src/index.ts"]
      }
    }
  }

WHY THIS PREVENTS PROBLEMS:

PROBLEM WITHOUT PATH ALIASES:
  // In services/auth-service/src/handlers/client.handler.ts
  import { KafkaTopics } from "../../../../packages/types/src/index.js";
  // ❌ Fragile: breaks if you move files
  // ❌ Unreadable: 4 levels of ../
  // ❌ Circular deps: hard to track

SOLUTION WITH ALIASES:
  import { KafkaTopics } from "@turtle/types";
  // ✅ Readable
  // ✅ Works regardless of file location
  // ✅ TypeScript compiler knows @turtle/types = ./packages/types

IMPORT FLOW FOR @TURTLE/TYPES FROM SERVICES/AUTH-SERVICE:

1. TypeScript compiler sees import { KafkaTopics } from "@turtle/types"
2. Checks tsconfig.json → finds path mapping
3. Resolves to packages/types/src/index.ts
4. Reads the file, finds export enum KafkaTopics { ... }
5. At RUNTIME (webpack/tsc):
   • Since .ts is in workspace, it gets cross-compiled
   • The actual import becomes const KafkaTopics = require("@turtle/types")
   • pnpm workspace symlinks make @turtle/types point to packages/types/src

WORKSPACE DEPENDENCIES IN PACKAGE.JSON:
  {
    "dependencies": {
      "@turtle/types": "*",
      "@turtle/config": "*"
    }
  }

  • "*" = use whatever version in packages/types/package.json
  • pnpm creates SYMLINKS, not copies (instant updates in dev)

VALIDATION CHECKLIST (what needs to be correct):

  ✅ Every service that uses @turtle/types:
     • auth-service ✓ (imports KafkaTopics, JWTPayload)
     • otp-service ✓ (imports KafkaTopics, OTPChannel)
     • user-service ✓ (imports UserType)
     • notification-service ✓ (imports KafkaTopics)

  ✅ Every app that uses @turtle/ui & @turtle/types:
     • client-app ✓ (imports OTPInput, ErrorMessage from ui)
     • advisor-app ✓ (imports OTPInput, GoogleOAuthButton, etc)

  ✅ tsconfig extends chain:
     • apps/client-app/tsconfig.json extends "../../tsconfig.base.json" ✓
     • services/auth-service/tsconfig.json extends "../../tsconfig.base.json" ✓

5. HEALTH CHECK SCRIPT (scripts/healthcheck.sh): Orchestration Foundation
================================================================================

WHY A DEDICATED SCRIPT?

In distributed systems, ORDER MATTERS:

  kafka broker starts   (takes 30s+ due to Zookeeper startup)
       ↓
  auth-service starts   (waits for kafka health)
       ↓
  client-app starts     (waits for auth-service health)

docker-compose ALREADY HAS HEALTHCHECKS, but scripts/healthcheck.sh goes further:

EXAMPLE FLOW:
  #!/bin/bash
  set -e

  echo "🔍 Checking service health..."

  check_health() {
    local service=$1
    local port=$2
    local url=$3
    
    echo -n "  $service ($port)... "
    if curl -sf --connect-timeout 2 "http://localhost:$port$url" > /dev/null 2>&1; then
      echo "✅ OK"
    else
      echo "❌ DOWN"
      exit 1
    fi
  }

  check_health "PostgreSQL"              5432 "/"
  check_health "Redis"                   6379 "/"
  check_health "Kafka"                   9092 "/"
  check_health "Auth-Service"            4000 "/health"
  check_health "OTP-Service"             4001 "/health"
  check_health "Client-App"              3000 "/"
  check_health "Advisor-App"             3001 "/"

  echo ""
  echo "✅ All services healthy!"
  exit 0

WHY EACH SERVICE?

  Service              Port  Endpoint     Why Check
  ────────────────────────────────────────────────────────────────
  PostgreSQL           5432  /            Can't run tests until DB exists; migrations need it
  Redis                6379  /            OTP cache, rate-limit buckets, JWT tokens must not lose state
  Kafka                9092  /            Event producers hang if broker unavailable
  Auth-Service         4000  /health      Returns { status: "ok", service: "auth-service" }
  Client-App           3000  /            Serves index.html; if not serving, users can't load UI

WHEN THIS RUNS:

  # CI/CD pipeline
  docker-compose up -d --build
  sleep 5  # brief pause for containers to start
  ./scripts/healthcheck.sh  # exits 0 if all healthy, 1 otherwise
  npm run test             # only if healthcheck passed

6. EVENT BUS ARCHITECTURE: Why Kafka (Not Synchronous HTTP)
================================================================================

THE DILEMMA:

OPTION A: SYNCHRONOUS HTTP (without Kafka):
  Client POST /auth/client/request-otp
    ↓
  Auth-Service receives request
    ↓
  Auth-Service calls OTP-Service HTTP endpoint
    ↓
  OTP-Service calls Twilio API (5s timeout)
    ↓
  Response returns to client

PROBLEMS:
  ❌ If Twilio is slow (network latency), client waits 5s-10s (poor UX)
  ❌ If OTP-Service is down, entire request fails (no resilience)
  ❌ Hard to retry — what if Twilio fails halfway?
  ❌ No audit trail of what happened

OPTION B: ASYNCHRONOUS EVENT BUS (Kafka) ← CHOSEN:
  Client POST /auth/client/request-otp
    ↓
  Auth-Service immediately publishes to Kafka topic "auth.otp.requested"
    ↓
  HTTP 202 response → Client gets instant confirmation
    ↓
  [Async]
  OTP-Service consumes event from topic
    ↓
  OTP-Service calls Twilio API (slow, no client waiting)
    ↓
  OTP-Service publishes "auth.otp.sent" event back
    ↓
  Notification-Service consumes events & logs them

WHY KAFKA?

1. DECOUPLING:
  Auth-Service doesn't know OTP-Service exists
  OTP-Service doesn't know Auth-Service exists
  They communicate only via Kafka topics
  → Can deploy/restart OTP-Service without affecting Auth-Service

2. EVENT REPLAY:
  Kafka stores messages in topics (default: 7 days retention)
  If OTP-Service crashes:
    • Consumer group offset tracks last processed message
    • On restart, it resumes from that offset
    • No missed events

3. FAN-OUT (One Event, Multiple Consumers):
  Topic: "auth.login.success"
    ↓
  Consumed by:
    • Notification-Service (sends email)
    • User-Service (updates last_login_at)
    • Analytics-Service (logs for dashboard)
  Only one event publishes → three things happen. Easy to add more.

4. SPEED:
  Kafka broker accepts message in ~1ms
  Returns 202 to client immediately
  Client doesn't wait for slow operations (Twilio, email, DB)

7. AUTHENTICATION FLOWS: Client vs Advisor
================================================================================

CLIENT-APP FLOW (OTP-ONLY):
  User enters phone/email
    ↓ POST /auth/client/request-otp
  Auth-Service publishes auth.otp.requested event
    ↓
  OTP-Service consumes, calls provider (Twilio/MSG91)
    ↓
  User receives SMS/Email with 6-digit code
    ↓ POST /auth/client/verify-otp
  Auth-Service validates Redis cache
    ↓
  Auth-Service issues JWT access token (15m) + refresh token (7d)
    ↓
  Client stores in:
    • localStorage: accessToken (XSS risk, but quick)
    • httpOnly cookie: refreshToken (CSRF protection, secure)
      ^ Sent automatically by browser; can't be stolen by JS
    ↓
  Client can now call /protected endpoints with Authorization: Bearer <accessToken>

WHY THIS FLOW?
  • Minimal friction: no password = lower entry barrier
  • OTP proves phone/email ownership
  • Used by: casual users, high-security needs (banking), phone-only demographics

ADVISOR-APP FLOW (USERNAME + PASSWORD + OTP 2FA + OAUTH):
  User visits login page

  [Branch 1: Traditional Login]
  User enters username + password
    ↓ POST /auth/advisor/login
  Auth-Service validates password hash (bcrypt, constant-time)
    ↓
  If password correct:
    Auth-Service publishes auth.otp.requested event
      ↓ OTP sent via SMS/Email
    ↓
  User enters OTP
    ↓ POST /auth/advisor/verify-otp
  Auth-Service validates OTP + password was correct
    ↓
  Issues JWT + refresh token

  [Branch 2: OAuth (Google)]
  User clicks "Sign in with Google"
    ↓
  Redirects to Google's /oauth/authorize?client_id=...&scope=...&redirect_uri=...
    ↓
  Google shows consent screen
    ↓
  Redirects back to /auth/google/callback?code=...
    ↓ POST /auth/advisor/oauth/google
  Auth-Service exchanges code for Google token
    ↓
  Auth-Service fetches user profile from Google (email, name)
    ↓
  Auth-Service creates/updates advisor in user-service
    ↓
  Issues JWT + refresh token (NO OTP fallback if using OAuth)

WHY THIS FLOW?
  • Username + password = trusted staff (advisors, employees)
  • OTP 2FA = prevents password spray/brute force
  • OAuth = SSO convenience, trusts Google's security
  • Separation: clients can't access advisor features, advisors can't use client app

8. TOKEN LIFECYCLE & REDIS CACHING
================================================================================

WHY REDIS, NOT JUST DATABASE?

ACCESS TOKEN (15 minutes):
  JWT issued with { userId, userType, role, exp: now + 15m }
  Stored in: localStorage (client-side)
  On each API call: Authorization: Bearer <token>
  Server validates JWT signature + expiration (NO REDIS LOOKUP)
    → Simple, fast, scales infinitely (no server state)

REFRESH TOKEN (7 days):
  JWT issued with { userId, sessionId, tokenId, exp: now + 7d }
  Stored in: httpOnly cookie (browser-only, CSRF safe)
  Stored in Redis: key=refresh_token:{tokenId}, value={sessionId, userId}
    → TTL = 7 days (auto-delete after 7 days)

  When client's accessToken expires (15m):
    Browser automatically sends httpOnly cookie
    POST /auth/refresh with refresh token
    Auth-Service looks up refresh_token_blacklist:{tokenId} in Redis
    If found → token was revoked, reject
    If not found → token is valid, issue new accessToken

WHY REDIS?
  • Speed: O(1) lookup, sub-millisecond
  • TTL: Automatic expiration (SETEX command)
  • Revocation: Logout = add to blacklist with 7d TTL
  • Scaling: Can run Redis cluster for high-traffic

IF REDIS IS DOWN:
  • Access tokens still work (JWT is self-contained, verified via signature)
  • Refresh would fail (can't check revocation list)
  • Graceful degradation: user stays logged in until accessToken expires

9. DOCKER NETWORK ISOLATION & DNS
================================================================================

INSIDE DOCKER COMPOSE NETWORK:
  Container name: auth-service
  Accessible as: http://auth-service:4000 (Docker DNS)
  From client-app container: curl http://auth-service:4000/health

  Container name: client-app
  Accessible as: http://client-app:3000 (Docker DNS)

VITE PROXY CONFIGURATION (in apps/client-app/vite.config.ts):
  proxy: {
    "/auth": {
      target:       "http://localhost:4000",  // ← DEV MODE
      changeOrigin: true,
    }
  }

IN PRODUCTION (DOCKER):
  • Vite builds to dist/index.html
  • pnpm preview serves static files from dist/
  • Client-side code makes fetch requests to /auth/...
  • BUT where is /auth proxied to?

SOLUTION: API_URL ENVIRONMENT VARIABLE:
  // apps/client-app/src/api/axios.ts
  const API_BASE_URL = process.env.VITE_API_URL ?? "http://localhost:4000";
  const axios = createAxiosInstance({
    baseURL: API_BASE_URL
  });

IN DOCKER:
  ENV VITE_API_URL=http://auth-service:4000

Now client-app → fetch to http://auth-service:4000/auth/... inside Docker network.
